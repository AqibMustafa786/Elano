# ELANO

Premium fashion storefront built with Next.js, TypeScript, Tailwind CSS, and Firebase.

## Firebase architecture

- Firebase Authentication handles customer identity.
- Cloud Firestore stores catalog, customer, order, and storefront data.
- Cloud Storage stores product and editorial images.
- Cloud Functions (2nd gen) handle trusted operations.
- Firebase Admin SDK is used only in Cloud Functions and trusted local scripts.
- App Check protects callable Functions.
- Firebase services and Functions are configured for `asia-south1` (Mumbai, India).
- Vercel hosts the Next.js application.

The public Firebase web configuration is supplied through `NEXT_PUBLIC_FIREBASE_*` variables. These values identify the Firebase project; they are not authorization controls. Firestore Rules, Storage Rules, Authentication, and App Check provide access control. Never put service-account credentials in a `NEXT_PUBLIC_*` variable or commit them.

## Local setup

1. Install the web dependencies:

   ```powershell
   npm install
   ```

2. Copy `.env.example` to `.env.local` and fill in the Firebase Web App configuration from Firebase Console → Project settings → Your apps. Add the App Check reCAPTCHA v3 site key after registering the web app with App Check.

3. In Firebase Console, enable Email/Password under Authentication → Sign-in method. Create the default Firestore database in `asia-south1` (Mumbai) if it does not already exist. Firestore's location cannot be changed after creation.

4. Install and compile the Functions package:

   ```powershell
   npm install --prefix functions
   npm run firebase:build
   ```

5. Start Next.js:

   ```powershell
   npm run dev
   ```

The newsletter callable requires App Check to be configured and the Functions backend to be deployed or running in the Firebase Emulator Suite.

## Admin dashboard access

Run the app from `D:\elano\anti-store`:

```powershell
npm run dev
```

Open `http://localhost:3000/admin`. The admin page supports Firebase email/password sign-in, verifies the `admin: true` custom claim, and provides store overview, product management, and analytics. Create the account in Firebase Authentication and grant its UID the claim using the trusted script below.

## Analytics

The protected `/admin/analytics` report is generated by the `getAnalyticsReport` callable. It checks the Firebase Admin custom claim and App Check token, reads date-filtered orders in 500-document pages, and returns aggregates only (never customer names, email addresses, or addresses). The dashboard supports today, yesterday, 7/30/90 days, this/previous month, this year, and custom ranges up to 366 days. It supports CSV export and printing.

### Firestore order fields used by business analytics

Only an order with a recognized `paymentStatus` (`paid`, `captured`, `succeeded`, `refunded`, or `partially_refunded`), a valid three-letter `currency`, a non-negative integer `totalMinor`, and a Firestore `createdAt` timestamp is included in recognized sales. Cancelled orders are excluded. Supported fields are:

- `status`: `pending`, `processing`, `awaiting_payment`, `completed`, `complete`, `delivered`, `cancelled`, or `canceled`.
- `paymentStatus`, `paymentIntentId`, `currency`, `totalMinor`, optional `subtotalMinor`, `refundAmountMinor`, and `discountMinor`.
- `userId`, `paymentMethod`, `couponCode`, and `items[]` with `productId`, `productName`, `categoryName`, `quantity`, and either `lineTotalMinor` or `unitPriceMinor`.

Gross revenue uses `subtotalMinor` when present, otherwise `totalMinor`; net revenue is `totalMinor` less the recorded `refundAmountMinor`. Values are grouped by currency and never converted or added across currencies. Duplicate `paymentIntentId` values are counted once. Orders without verified payment fields remain in order totals and are surfaced as unverified, but do not contribute to revenue. Returning buyers means buyers with at least two verified paid orders inside the selected period; it is not a lifetime repeat-purchase metric.

The report also reads product inventory and customer document counts. Low stock currently means 1–5 units. Product views, add-to-cart events, checkout starts, and purchases come only from GA4 and are clearly separated from Firestore paid orders. Fields not present in the current order/customer model (for example refunds beyond `refundAmountMinor`, geographic data, variants without a `variants` array, or lifetime customer value) are not inferred.

### Configure GA4 reporting

1. Enable the Google Analytics Data API for the Firebase project's Google Cloud project.
2. Grant the deployed Cloud Functions runtime service account Viewer access to the GA4 property.
3. Copy `functions/.env.example` to `functions/.env.elano-ac833` and set `GA4_PROPERTY_ID` to the numeric GA4 property ID. Do not put service-account keys in the repository; the function uses Application Default Credentials.
4. Set `NEXT_PUBLIC_FIREBASE_MEASUREMENT_ID` to the GA4 web measurement ID in the web environment. The storefront sends `page_view`, `view_item`, `add_to_cart`, and `search` events when this value is configured.
5. Redeploy Functions and the web app. Verify GA4 events separately from Firestore orders. `begin_checkout` and `purchase` events require a secure checkout/order workflow and are intentionally not fabricated by the current cart.

Without the property ID, API enablement, or service-account access, the dashboard shows the GA4 error and leaves traffic metrics unavailable. It never substitutes zeros for a failed GA4 query.

## Firebase CLI and deployment

Install the Firebase CLI if needed, then authenticate:

```powershell
npm install --global firebase-tools
firebase login
firebase use elano-ac833
```

Confirm the existing Firestore database location before deploying:

```powershell
firebase firestore:databases:list --project elano-ac833
```

The configured Functions region is `asia-south1`; it should be close to the Firestore database region. Do not create a replacement database to change region.

Deploy Firestore Rules, indexes, Storage Rules, and Functions:

```powershell
npm run firebase:deploy
```

Cloud Functions deployment requires the Firebase project to have billing enabled (Blaze plan) and the required Google Cloud APIs enabled. The deploy command will build the Functions package first.

For local development with emulators, use:

```powershell
firebase emulators:start --only auth,firestore,functions,storage
```

## App Check

1. Register the web app in Firebase App Check with reCAPTCHA v3.
2. Set `NEXT_PUBLIC_FIREBASE_APPCHECK_SITE_KEY` to only the reCAPTCHA v3 site key in `.env.local` and in Vercel's environment variables. Do not include the variable name in its value and do not leave the `YOUR_RECAPTCHA_SITE_KEY` placeholder.
3. Monitor App Check requests in Firebase Console before enabling enforcement for other Firebase products.
4. Callable Cloud Functions enforce App Check.

### Firebase sign-in domain errors

If sign-in shows `auth/unauthorized-domain`, open Firebase Console → Authentication → Settings → Authorized domains and add the exact host used by the app. For the local URLs used in this workspace, add both `localhost` and `127.0.0.1`; do not include ports such as `3000` or `3001`. Add the production hostname before deployment. Firebase authorizes the hostname, not the port.

The Admin SDK bypasses Firestore and Storage client Rules by design. Cloud Functions must validate inputs, authorization, prices, and stock before writing privileged records.

## First Super Admin

1. Create the initial account through Firebase Authentication.
2. Obtain that account's Firebase Auth UID from Firebase Console.
3. Authenticate trusted local tooling with Google Application Default Credentials:

   ```powershell
   gcloud auth application-default login
   npm --prefix functions run grant-admin -- <firebase-auth-uid>
   ```

The script assigns the `admin: true` custom claim to that UID. Do not add a public endpoint that lets users grant themselves admin access. The user must sign out and sign back in to refresh the ID token and receive the claim.

## Vercel environment

Set these variables in the Vercel project for the appropriate deployment environments:

- `NEXT_PUBLIC_FIREBASE_API_KEY`
- `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`
- `NEXT_PUBLIC_FIREBASE_PROJECT_ID`
- `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`
- `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`
- `NEXT_PUBLIC_FIREBASE_APP_ID`
- `NEXT_PUBLIC_FIREBASE_MEASUREMENT_ID` (optional)
- `NEXT_PUBLIC_FIREBASE_APPCHECK_SITE_KEY`

Only the Firebase Web App configuration belongs in these public variables. Keep Admin SDK credentials out of the browser and out of source control.

## Current implementation boundary

The Firebase client, App Check initialization, callable newsletter and analytics functions, Firestore and Storage Rules, indexes, trusted admin-claim script, protected admin overview, product CRUD, published-product storefront query, wishlist, and local cart are in place. Secure checkout, payment processing, order creation/refunds, customer sign-up, and persistent high-volume analytics rollups still need to be implemented and verified against the configured Firebase project. Until then, revenue is only reported for existing verified order documents; an empty order collection correctly produces no sales.
